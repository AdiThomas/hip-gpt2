# v1 — coalesced global memory access

Source: `src/kernels/v1_coalesced.hip`. Registry name: `v1` (FP32 only).

## Idea

Factory analogy: **threads are workers, global memory is the warehouse, LDS and registers are the parts bins beside the line.** v0 sent neighbouring workers to 16 different shelves at once. v1 changes nothing about *what* is computed, only *which worker takes which item*: neighbouring workers now take neighbouring items from the same shelf, so one truck trip (one wide memory transaction) serves a whole group of workers.

The algorithm and the loop are identical to v0. Only the thread-to-element mapping changes.

## What the code does

- `gemm_v1_kernel`: `col = blockIdx.x * blockDim.x + threadIdx.x`, `row = blockIdx.y * blockDim.y + threadIdx.y`. So **`threadIdx.x` walks along columns**, the contiguous direction of B and C.
- Block `kV1BlockX x kV1BlockY = 32 x 8` = 256 threads. 32 floats = 128 bytes = one cache line, so a wave's x-run covers exactly one line of B and C (wave64 covers two rows of 32, wave32 one row).
- Per k step: B loads are 32 consecutive floats per row-group (coalesced); the A load `a[k]` is one address shared by all lanes of a row (a broadcast, one transaction); the C store is full 128-byte lines.
- `launch_v1` swaps the grid roles relative to v0: `grid.x` over columns, `grid.y` over rows.

## Theory-based prediction

- The bytes the *program* asks for are unchanged: still 8 bytes per FMA, 4 bytes/FLOP. What changes is the number of memory transactions. In v0 one A load per wave touched about 16 cache lines; in v1 B needs about 1 to 2 lines and A needs 1 (broadcast). The lines fetched per FMA drop by roughly an order of magnitude.
- It is still memory/L2-bound and there is still no reuse between blocks beyond the cache: every block re-reads whole rows of A and columns of B. Arithmetic intensity is unchanged, so the roofline position moves *up* (better use of bandwidth) but not *right*.

## Interview questions

1. **v0 and v1 do the same arithmetic and the same loop. Why is v1 faster?** Same number of requested bytes, but v1 lets the hardware merge a wave's loads and stores into a few wide cache-line transactions, while v0 splits them into many narrow ones. Memory systems are priced per transaction.
2. **Which accesses are coalesced in v1?** B loads (consecutive columns across lanes), C stores (same), and A loads are a broadcast (all lanes of a row read the same element). In v0, A and C were strided by a row length.
3. **Why does the block use 32 x 8 and not 16 x 16?** 32 consecutive floats is a whole 128-byte line, so each wave row is one full line. 16 would waste half a line, and the wave would be split across more rows.
4. **v1 is still far from peak. What is the next bottleneck and what does it tell you?** Arithmetic intensity is still 0.25 FLOP per byte requested; each block re-reads A and B from global memory with no reuse under our control. Fixing the access pattern cannot beat that; the fix is to change the algorithm so loaded data is reused (v2).
