# v5 — matrix-core instructions (MFMA on Instinct, WMMA on NVIDIA and RDNA3)

Source: `src/kernels/v5_matrix_core.hip` plus one of three included files chosen by CMake: `v5_mfma.inc` (AMD Instinct, e.g. MI300X), `v5_wmma_nvidia.inc` (NVIDIA tensor cores, e.g. RTX 4060) or `v5_wmma_rdna3.inc` (experimental, Radeon gfx11). Registry name: `v5` (FP16 inputs, FP32 output). On the CPU backend `v5` is listed as unavailable.

**Not compiled or run yet.** All three paths are written from documentation only. Treat everything below as design intent until `gemm_bench --kernel v5 --test` passes on hardware.

## Idea

Factory analogy: **threads are workers, global memory is the warehouse, LDS and registers are the parts bins beside the line.** Up to v4 every worker multiplied one pair of numbers per step with a hand tool. A matrix core is a purpose-built press: a whole wave of workers hands it two small 16 x 16 blocks of numbers and it produces the 16 x 16 product update in one instruction (4096 multiply-adds). The workers still unload the trucks and stock the bins exactly as in v4; they just swap the hand tools for the press.

## What the code does

- The block tile is 64 x 64 x 32 with 4 waves in a 2 x 2 grid. Each wave owns a 32 x 32 piece of C = 2 x 2 tiles of 16 x 16, held as FP32 accumulators (`V5Accum`).
- Global-to-LDS staging is **literally the same code as `v4_fp16`** (`f16_load_slab`, `f16_store_slab`, double-buffered LDS, one barrier per slab). Only the inner product and the epilogue differ. This is on purpose: every CPU run of `v4_fp16` then tests v5's address arithmetic, zero padding and vector-load rules, so what is untested on CPU is limited to the inner product and the store.
- Contract each `.inc` provides: `kV5WaveSize`, `kV5Waves = 4`, `kV5Threads`, `V5Accum`, `v5_acc_zero`, `v5_mma_slab` (all BK/16 = 2 k-steps of one LDS slab), `v5_store` (guarded epilogue).
- **MFMA path** (`v5_mfma.inc`): wave64, 256 threads, `__builtin_amdgcn_mfma_f32_16x16x16f16(a, b, c, 0, 0, 0)`. A and B fragments are 4 halves per lane, the accumulator 4 floats per lane. The lane layout (lane `l`: A row `l % 16`, k = `4*(l/16)+j`; D column `l % 16`, rows `4*(l/16)+j`) is tabulated in the file's header comment, taken from AMD's Matrix Instruction Calculator. A comes from LDS as one 8-byte read; B is `Bs[k][n]` (k-major), so a B fragment is 4 scalar 2-byte reads, one row apart.
- **NVIDIA path**: `nvcuda::wmma` 16x16x16 half-in float-accumulate fragments loaded from LDS with explicit strides (`kF16LdA = 40`, `kF16LdB = 72` halves), 128 threads (4 warps). The fragment layout is opaque, so the epilogue goes through a per-warp LDS scratch tile and then a guarded copy to C.
- **RDNA3 path** (experimental, needs `-DHIPGPT2_ENABLE_RDNA3_WMMA=ON`): `__builtin_amdgcn_wmma_f32_16x16x16_f16_w32`, wave32.
- Edge handling: staging zero-pads partial tiles in LDS, and the epilogue writes only `row < M && col < N`, so any M, N, K is covered.

## Theory-based prediction

- One MFMA does `16 * 16 * 16 = 4096` FMAs (8192 FLOPs) for a wave. The scalar path needs 64 lanes x 64 FMA instructions for the same work. The matrix-core FP16 peak is several times the FP32 vector peak (look up your device's datasheet values: `{{device_fp32_vector_peak_tflops}}`, `{{device_fp16_matrix_peak_tflops}}`), so v5 can in principle go far beyond v4.
- It will not get near peak with this tile. Per 32-deep slab a block does `2 * 64 * 64 * 32 = 262144` FLOPs from `(64*32 + 32*64) * 2 = 8192` bytes of global data: **32 FLOPs per global byte**. A matrix-core peak needs far more reuse than that, so the kernel should end up **feed-bound** (LDS reads and global loads), not compute-bound. The k-major B layout (4 strided 2-byte LDS reads per lane on MFMA, 16 on RDNA3 WMMA) makes it worse.
- Expect: clearly faster than `v4_fp16`, clearly slower than hipBLAS. Next steps if you want more: transpose B in LDS, bigger block and wave tiles, deeper pipelining.

## Profiler counters to look at

AMD (`scripts/profile_amd.sh v5 4096`, rocprof-compute) / NVIDIA (`scripts/profile_nvidia.sh v5 4096`, Nsight Compute):

- **Matrix-core utilisation**: rocprof-compute's MFMA busy / MFMA instruction counts; Nsight's tensor pipe utilisation (for example `sm__pipe_tensor_op_hmma_cycles_active.avg.pct_of_peak_sustained_active`). Predicted: well below peak.
- **LDS read instructions and bank conflicts**: the strided B-fragment reads are the suspect. The source header notes a possible 2-way conflict on the MFMA B reads (a `Bs` row is 36 words with `kF16PadB = 8`); on MI300X check the `SQ_LDS_BANK_CONFLICT` counter.
- **Barrier stalls and memory-wait stalls**.
- **Achieved FLOPS on the roofline plot** against the matrix-core (FP16) roof, not the FP32 vector roof.
- **Occupancy**, registers, LDS per block.
- Check first that the compiler really emitted matrix instructions (disassemble: look for `v_mfma_f32_16x16x16_f16` on AMD, `HMMA` in SASS on NVIDIA).

## Interview questions

1. **What does one MFMA / WMMA instruction compute, and who executes it?** A whole wave cooperatively computes `D = A * B + C` for a 16 x 16 x 16 block: each lane supplies a few elements of A and B and receives a few elements of D. The matrix unit does 4096 multiply-adds per instruction at a much higher rate than the vector units.
2. **Why do the inputs stay FP16 but the accumulators FP32?** FP16 inputs halve memory traffic and match the hardware's fast path; summing thousands of products needs FP32 range and precision, so the accumulators are FP32. The test tolerance is 1e-3 against a reference fed the same rounded inputs.
3. **Why did you reuse the `v4_fp16` staging code instead of writing v5 from scratch?** No GPU was available while writing it. Sharing the staging code means the CPU tests of `v4_fp16` exercise v5's data movement, so what could be wrong on hardware is confined to the lane layout and the epilogue.
4. **Why is v5 far from peak, and what is the first fix?** At 32 FLOPs per global byte and with strided B-fragment LDS reads, the kernel cannot feed the matrix cores fast enough. First fixes: store B transposed in LDS (so a B fragment is one vector read), enlarge the block and wave tiles for more reuse, and add deeper software pipelining.
