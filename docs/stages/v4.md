# v4 — vectorized loads + double buffering

Source: `src/kernels/v4_vec_dbuf.hip` (FP32), `src/kernels/v4_fp16.hip` with the shared staging code in `src/kernels/fp16_staging.inc` (FP16 inputs). Registry names: `v4`, `v4_fp16`. `v4` is also what the LLM engine calls for prefill (`gemm_fp32_best`).

## Idea

Factory analogy: **threads are workers, global memory is the warehouse, LDS and registers are the parts bins beside the line.** v3 had two inefficiencies. (1) Workers carried parts one at a time, though a truck can move four at once (vector loads). (2) Everyone stopped at the dock waiting for the next delivery before starting the next batch. In v4 the next delivery is ordered *before* the current batch is assembled, so it arrives while the line is busy (double buffering), and each trip carries four parts.

## What the code does

- Same tile as v3: 64 x 64 block tile, `kV4BK = 16`, 4 x 4 per thread, 256 threads. This keeps the v3 to v4 difference confined to vectorization and double buffering.
- **Vector loads**: each thread moves exactly one `float4` of A and one of B per slab (static asserts enforce `64*16/4 == 256`). LDS operands are read as `float4` and C is stored as `float4` where legal.
- **Alignment safety** (this is where bugs hide): `launch_v4` computes `vec_a = aligned16(dA) && K % 4 == 0`, `vec_b = aligned16(dB) && N % 4 == 0`, `vec_c` likewise for C, and picks one of four template instantiations `gemm_v4_kernel<kVecA, kVecB>`. Misaligned pointers (for example a view into the middle of an allocation) or odd strides take the scalar-load path. Tails are loaded scalar and never read past the end of A or B.
- **Double buffering**: `As[2][16][64 + 4]` and `Bs[2][16][64]` (about 17 KiB of LDS). Each loop iteration: (1) `load_slab(next)` into registers `a_reg`/`b_reg`; (2) compute the current slab from LDS; (3) `store_slab(cur ^ 1)` parks the prefetched slab in the *other* buffer; (4) **one** `__syncthreads()`. Step 3 needs no extra barrier because that buffer was last read in the previous iteration, which ended with a barrier.
- Output mapping becomes *blocked* (thread owns rows `ty*4+i`, columns `tx*4..tx*4+3`) so a thread's four operands are adjacent in LDS and one `float4` read gets them. `As` is padded by 4 floats so rows stay 16-byte aligned.
- `v4_fp16` applies the same recipe to `__half` inputs: BK = 32, 16-byte (8-half) chunks, FP32 accumulation, conversion to float in registers. Its staging code (`f16_load_slab` / `f16_store_slab`) is shared with v5.

## Theory-based prediction

- Same bytes per FLOP as v3 (1/16 byte/FLOP global, 4 FLOPs per LDS word). The improvements are in *instruction count* and *latency*: 4x fewer global load/store instructions, `ds_read_b128` (vector LDS reads) instead of four `ds_read_b32`, and the global latency (hundreds of cycles) is hidden behind `16 * 16 = 256` FMAs per thread per slab instead of exposed.
- One barrier per slab instead of two.
- Costs: LDS doubles to about 17 KiB and the prefetch registers (8 floats) raise register use, so occupancy may drop a little. Expect a moderate gain over v3, and a result that is now compute/issue-bound at large sizes: FP32 FMA throughput is the ceiling, and the vendor library (hipBLAS) will still be well ahead.
- `v4_fp16` predicted bottleneck: it is still FP32 FMAs, plus about 8 conversions (`v_cvt_f32_f16`) per 16 FMAs, so it should be near `v4` in speed even though the inputs are half the size. That is the case for matrix cores (v5).

## Profiler counters to look at

Nsight Compute (`scripts/profile_nvidia.sh v4 4096`) / rocprof-compute (`scripts/profile_amd.sh v4 4096`):

- **Global load/store instruction count**: about 4x fewer than v3.
- **Stall reasons**: long-scoreboard / memory-wait stalls should shrink; barrier stalls roughly halve.
- **VALU / FMA utilisation** and the roofline dot: closer to the compute roof.
- **LDS bank conflicts**: predicted near zero with the +4 float pad. Check anyway: the transposing scalar stores into `As` are the likely culprit if not.
- **Occupancy, registers per thread, LDS per block**: the price paid for double buffering. Compare with v3.
- For `v4_fp16`: share of conversion instructions in the instruction mix.

## Interview questions

1. **When is a `float4` load legal, and how does the kernel guarantee it?** The address must be 16-byte aligned, and a vector must not straddle the end of a row or the buffer. The launcher checks that the base pointer is 16-byte aligned and that the row stride (K for A, N for B and C) is a multiple of 4, then selects a template instantiation; otherwise a scalar path runs, and tails are always scalar. HIP-CPU cannot catch a misaligned vector load, so the GPU `--test` shapes matter.
2. **Explain the double-buffering schedule.** Load slab s+1 from global memory into registers, compute slab s from LDS, write the registers to the other LDS buffer, barrier. The global loads are in flight during the compute, so latency is hidden. Two LDS buffers mean writes for s+1 never touch the buffer being read for s, so one barrier per slab is enough.
3. **What did you trade away for it?** More LDS (about 17 KiB vs about 8 KiB) and more registers (prefetch registers), so fewer resident blocks per compute unit; and code complexity: four template variants plus a vec-C flag. It is worth it only if the latency it hides exceeds the occupancy it costs, which the profiler has to confirm.
4. **v4 still loses to hipBLAS. Where would you look for the remaining gap?** Larger or non-square block/thread tiles (more reuse per thread), better instruction scheduling, finer tuning per architecture, more waves in flight, and on FP16 or with matrix cores, using the matrix units at all. The roofline plot and the VALU/FMA utilisation figure say which of these matters.
