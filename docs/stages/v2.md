# v2 — LDS tiling

Source: `src/kernels/v2_lds_tiled.hip`. Registry name: `v2` (FP32 only).

## Idea

Factory analogy: **threads are workers, global memory is the warehouse, LDS and registers are the parts bins beside the line.** In v0/v1 each worker walked to the warehouse for every part, even though the worker next to them needed the same parts. In v2 a team of workers (one block) makes one big trip together, unloads a small batch of A parts and B parts into a shared parts bin beside the line (LDS), and everyone assembles from the bin. Each part fetched from the warehouse now serves many workers.

LDS ("local data share" on AMD, "shared memory" on NVIDIA) is a small, fast, software-managed on-chip memory shared by all threads of a block. The cache that v1 hoped for becomes a scratchpad that the code controls.

## What the code does

- Constant `kV2Tile = 32`: a 32 x 32 block of 1024 threads (the HIP maximum) owns a 32 x 32 tile of C. Two `__shared__ float` tiles (`As`, `Bs`, 32 x 32 each = 8 KiB total).
- Loop over K in steps of 32 (`k0`). In each step thread `(ty, tx)` loads **one** element of the A tile (`A[row][k0+tx]`) and **one** of the B tile (`B[k0+ty][col]`). Both loads are contiguous across `tx`, so they are coalesced. Elements outside the matrix are written as 0, so the inner loop needs no bounds checks (this is also what makes arbitrary M, N, K correct).
- `__syncthreads()` once the tile is complete, then `for k in 0..31: acc += As[ty][k] * Bs[k][tx]`, then a second `__syncthreads()` before the next tile overwrites LDS.
- Only the final store is guarded (`row < M && col < N`).

## Theory-based prediction

- Global traffic: each loaded element is used by 32 threads. Bytes per FMA fall from 8 to 8/32 = 0.25, i.e. **0.125 bytes/FLOP instead of 4**, a 32x cut in global traffic.
- The new cost is on chip: the inner loop does **2 LDS reads per FMA** (1 FLOP per LDS read), plus two barriers per 32-step slab. So the limit moves from HBM/L2 to LDS bandwidth and instruction issue. `As[ty][k]` is a broadcast (all lanes of a row read one word); `Bs[k][tx]` is stride-1 across lanes; so bank conflicts should be near zero.
- Expect a large jump over v1 and VALU (math unit) utilisation still well under half.

## Interview questions

1. **Why does tiling help, in numbers?** A TxT tile loads 2*T*T elements per K-slab but does T*T*T FMAs from them, so each loaded element is reused T times. With T = 32 global bytes per FMA drop from 8 to 0.25. The reuse moves from hoped-for caching to a scratchpad the programmer controls.
2. **Why two `__syncthreads()` per slab?** The first makes sure the whole tile is in LDS before anyone reads it; the second makes sure everyone has finished reading before the next slab overwrites it. Skipping either is a race that produces wrong results intermittently.
3. **Why write zeros into LDS for out-of-range elements?** So the inner loop can run all 32 steps without conditionals, and zeros contribute nothing to the sum. It keeps the hot loop branch-free and handles any M, N, K.
4. **What is a bank conflict and does v2 have them?** LDS is split into banks (32 or more); if several lanes of a wave access different addresses in the same bank at once, those accesses are serialized. v2's `As[ty][k]` reads are broadcasts (same address, no conflict) and `Bs[k][tx]` is stride-1 (one bank per lane), so it should have almost none.
