# v0 — naive GEMM (one thread per output element)

Source: `src/kernels/v0_naive.hip` (FP32), `src/kernels/v0_fp16.hip` (same thing with `__half` inputs). Registry names: `v0`, `v0_fp16`.

## Idea

The factory analogy used in every stage doc: **threads are workers**, **global memory (HBM) is a huge warehouse across town**, and **LDS (on-chip shared memory) and registers are the parts bins beside the assembly line**. A GEMM computes `C = A * B`; each output number `C[row][col]` needs a row of A and a column of B multiplied pairwise and summed.

v0 gives one worker one output number. Each worker drives to the warehouse for every single part: for each of the K steps it fetches one A value and one B value, multiplies, adds, and drives back for the next pair. Nothing is kept beside the line. It is correct and simple, and it is the baseline every later stage is measured against.

## What the code does

- `gemm_v0_kernel`: `row = blockIdx.x * blockDim.x + threadIdx.x` and `col = blockIdx.y * blockDim.y + threadIdx.y`, so **`threadIdx.x` walks down rows**. Then a plain loop `for k in 0..K: acc += a[k] * b[k*N]` straight from global memory. Threads outside the matrix (`row >= M || col >= N`) do nothing, so any M, N, K works.
- Block shape `kV0BlockX x kV0BlockY = 16 x 16` (256 threads). `launch_v0` rounds the grid up, with `grid.x` over rows and `grid.y` over columns.
- The x-to-row mapping is deliberate. It is the "textbook" way to write it and the *uncoalesced* way, so v1 can show what fixing only the mapping is worth.
- `v0_fp16` is the same kernel with `__half` inputs, converted to float per product, **FP32 accumulator**, FP32 output.

## Theory-based prediction

- Per FMA (2 FLOPs) the thread issues two 4-byte loads: 8 bytes / 2 FLOP = **4 bytes of load traffic per FLOP**, with no reuse except what the L1/L2 caches happen to catch.
- Within a wave, the 16 x-neighbours are 16 *different rows*, so one load of `A[row][k]` touches 16 cache lines `K*4` bytes apart, and each C store is 16 scattered 4-byte pieces. Loads of B are broadcast-like (lanes with the same `y` read the same address).
- Prediction: memory-bound, and bound by *transaction count* rather than by bytes actually needed. Expect a tiny fraction of peak FLOPS. Expect performance to fall further at large sizes, where each thread's row of A (`K*4` bytes) and the column of B no longer sit in cache.

Run `scripts/profile_nvidia.sh v0 4096` (Nsight Compute) or `scripts/profile_amd.sh v0 4096` (rocprof-compute). Counter and panel names vary by tool version; use the tool's own search.

- **Coalescing**: Nsight: sectors per request for global loads (`l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum` divided by `l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum`; 32 bytes per sector, so 4 is ideal for a warp reading 128 contiguous bytes, up to 32 is worst case). rocprof-compute: the vector L1 / texture-addresser coalescing and "cache lines per instruction" metrics.

- **Achieved DRAM / HBM bandwidth** vs peak, and the roofline position (far left, far below the memory roof or at least far below the compute roof).
- **Occupancy**: high; it does not help when every wave is waiting on memory.

## Interview questions

1. **Why is v0 slow if it does the "obvious" number of FLOPs?** It is limited by memory, not arithmetic. Every FMA needs two loads from global memory (4 bytes per FLOP), nothing is reused on chip, and the access pattern makes each wave touch many cache lines per instruction. The GPU's math units sit idle waiting for data.
2. **What does "coalesced" mean, and is v0 coalesced?** A wave's loads are coalesced when neighbouring lanes read neighbouring addresses, so the hardware serves the whole wave with a few wide transactions. v0 maps `threadIdx.x` to rows, so the A loads and C stores are strided by a full row; it is mostly uncoalesced (B is partly broadcast).
3. **Why accumulate in a register `acc` instead of updating `C` each step?** A register is free; writing C every step would add a global store per FMA. One store at the end is the minimum, and the same pattern is what lets later stages keep many accumulators in registers.
4. **Why does `v0_fp16` accumulate in FP32?** FP16 has about 3 decimal digits; summing K = 4096 products in FP16 loses accuracy and can overflow. FP16 inputs with an FP32 accumulator is also what matrix cores do, so v0_fp16 is the right reference for v5.
