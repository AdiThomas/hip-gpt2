# v3 — register blocking (4x4 outputs per thread)

Source: `src/kernels/v3_reg_blocked.hip`. Registry name: `v3` (FP32 only).

## Idea

Factory analogy: **threads are workers, global memory is the warehouse, LDS and registers are the parts bins beside the line.** v2 workers each built one product and went to the shared bin twice per assembly step. In v3 each worker builds a 4 x 4 grid of 16 products at once and keeps all 16 partial results in their own hands (registers). With 4 parts from the A bin and 4 from the B bin, a worker can do 16 assemblies, so the walks to the shared bin become rare relative to the work.

Registers are the fastest storage on the chip, private to each thread. Reusing a value from a register costs nothing.

## What the code does

- Constants: block tile `kV3BM x kV3BN = 64 x 64`, K-step `kV3BK = 16`, per-thread tile `kV3TM x kV3TN = 4 x 4`, so `16 x 16 = 256` threads (`kV3Threads`).
- LDS: `As[kV3BK][kV3BM + kV3PadA]` stores the A tile **transposed** (`As[k][m]`) with one float of padding per row, and `Bs[kV3BK][kV3BN]`. About 8 KiB.
- Cooperative load: loops of `e = tid; e += 256` fill the A tile (consecutive threads read consecutive k of one A row) and the B tile (consecutive threads read consecutive columns). Out-of-range elements become 0.
- Inner loop per `kk` in 0..15: load 4 A values and 4 B values from LDS into registers `a[4]`, `b[4]`, then a 4 x 4 outer-product update `acc[i][j] += a[i] * b[j]`: **16 FMAs per 8 LDS reads**.
- Output mapping is *strided*: thread `(ty, tx)` owns rows `ty + 16*i` and columns `tx + 16*j`, so for each `j` the 16 x-neighbours read 16 consecutive `Bs` words and later write 16 consecutive C floats.
- Both tile loads and the final store are bounds-guarded, so any M, N, K works. Two `__syncthreads()` per slab (still no double buffering).

## Theory-based prediction

- LDS side: v2 did 2 LDS reads per FMA (1 FLOP per LDS read). v3 does 8 reads per 16 FMAs = 32 FLOPs / 8 = **4 FLOPs per LDS read**, 4x better.
- Global side: a 64 x 64 tile reuses each loaded element 64 times (v2: 32). Per slab: loads `(64 + 64) * 16 * 4 = 8192` bytes for `2 * 64 * 64 * 16 = 131072` FLOPs, i.e. **1/16 byte per FLOP**, half of v2's 1/8.
- Cost: 16 accumulators plus 8 operands in registers per thread, so more registers but still modest.
- New bottleneck: **global-load latency**. The next slab is only requested after the barrier at the end of the current one, so the block waits while it flies. Expect VALU busier than v2 but with stalls on memory waits and barriers.

## Interview questions

1. **What does register blocking buy you?** Operands are loaded once into registers and reused across a whole sub-tile. A 4 x 4 per-thread tile needs 8 operand loads for 16 FMAs; a 1 x 1 tile needs 2 loads for 1 FMA. It raises FLOPs per LDS read from 1 to 4 and leaves the math units, not the LDS port, as the limit.
2. **Why is A stored transposed in LDS, with a pad?** Transposing (`As[k][m]`) makes a thread's A operands for one k lie along a row, so they are read together. The extra float per row shifts successive rows into different banks, so the transposing store (which strides across rows) avoids bank conflicts.
3. **What is the trade-off of a bigger per-thread tile?** More reuse (higher arithmetic intensity) but more registers per thread, fewer threads resident per compute unit (lower occupancy), and more latency left unhidden. The constants `kV3TM/kV3TN` make this easy to experiment with.
4. **Why does the strided output mapping (rows `ty + 16*i`) beat a blocked one here?** With strided columns, the 16 lanes of a row read 16 consecutive `Bs` words and write 16 consecutive C floats, so LDS reads and global stores are conflict-free and coalesced. (v4 switches to a blocked mapping so each thread's four operands are adjacent and can be read as one `float4`; it is a trade between scalar-friendly and vector-friendly layouts.)
