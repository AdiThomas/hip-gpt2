The problem

A matrix multiply C = A × B of two N × N matrices costs 2N³ floating-point operations: for N = 4096. Almost everything in a transformer is one. A GPU can do arithmetic far faster than it can fetch numbers from its memory, so the whole game is how many times each number gets used once it's on the chip.

The yardstick is hipBLAS, the vendor library (on NVIDIA it calls cuBLAS). Every kernel is first checked against a double-precision CPU reference on awkward shapes (1×1×1, primes, sizes that don't divide the tile). Only then is it timed: the median of 100 launches.

Climbing the ladder

Each stage changes one idea. The numbers are measured at N = 4096. The "why" behind each one is what I expected from the design: hypothesis marks claims I haven't yet confirmed with profiler counters.

v0

One thread per output. Each thread loops over K, reading A and B straight from memory: 8 bytes fetched for every 2 FLOPs. Neighbouring threads walk down rows, so their reads land far apart. GFLOP/s, of hipBLAS.

v1

Coalescing. Same loop. I only changed which thread computes which element, so neighbouring threads read neighbouring addresses and the hardware can serve a whole group's loads in a few wide transactions. faster ().

v2

Shared-memory tiling. A 32 × 32 block loads tiles of A and B into on-chip shared memory (LDS) once and reuses each value 32 times. Only , much less than the cut in memory traffic suggests. hypothesis The 4060's caches were already catching much of v1's reuse, and v2 now pays two LDS reads per multiply-add.

v3

Register blocking. Each thread computes a 4 × 4 patch, keeping 16 running sums in registers, so every LDS read feeds 4 multiply-adds instead of 1. (). This is the biggest jump after coalescing.

v4

Vector loads and double buffering. 16-byte float4 loads when the pointers are aligned (the launcher checks and picks one of four variants), and the next tile is fetched while the current one is computed. more, reaching : of hipBLAS, and at N = 1024.

Overall that's from v0 to v4. v4 still uses only about of the card's TFLOPS FP32 datasheet peak. hipBLAS, at , shows how much headroom is left.

v5: tensor cores

Modern GPUs have matrix units that do a whole 16 × 16 × 16 block of multiply-adds in one instruction: MFMA on AMD Instinct, WMMA on AMD RDNA3, and tensor cores (nvcuda::wmma) on NVIDIA. v5 keeps v4's FP16 data movement exactly and swaps only the inner product. On the 4060 that means the nvcuda::wmma path. It compiled and passed every correctness shape on the first try.

It reaches TFLOP/s at N = 1024 ( the scalar FP16 kernel) but falls to at 8192, while hipBLAS keeps climbing. hypothesis The drop starts roughly where the matrices outgrow the card's 24 MB L2 cache. From there, v5's 64 × 64 tiles and strided B-fragment reads from LDS can't hide main-memory latency. That's the first thing I'll check with Nsight Compute. Note that hipBLAS FP16 writes FP16 output and may accumulate in FP16. It's a speed reference, not a like-for-like comparison.

From kernels to a language model

GPT-2 small (124M parameters, 12 layers) is small enough to read in an afternoon and real enough to expose everything that matters. The engine is C++/HIP: a byte-level BPE tokenizer written from scratch (checked token for token against OpenAI's), a safetensors loader, kernels for embedding, layer norm, GELU, attention and the LM head, and a KV-cache.

Generation has two phases with opposite characters:

  • Prefill processes the whole prompt at once, so the linear layers are real matrix multiplies and use the v4 kernel. 86 prompt tokens take ms.
  • Decode makes one token at a time. Every weight is read once per token for 2 FLOPs per 4 bytes, so no amount of tiling helps. The limit is streaming ~500 MB of weights per token. At the 4060's GB/s (datasheet), that caps decode at about tokens/s.

The engine decodes at of that bandwidth ceiling, the speed of Hugging Face GPT-2 in plain PyTorch eager mode on the same GPU (FP32, with its KV cache). PyTorch here pays Python and kernel-launch overhead on every one of its small ops. torch.compile or CUDA graphs would close much of that gap, so read this as "beats the default path", not "beats PyTorch". The KV-cache matters a lot: without it, every step recomputes the whole sequence and decode falls to tokens/s.

One prediction didn't hold up. I wrote attention twice: a naive three-kernel version and a fused decode kernel that keeps the scores in on-chip memory. Over three runs each, fused averaged tokens/s and naive , and the ranges overlap. At a ~200-token context, attention is a small slice of each decode step next to reading the weights, so fusing it buys nothing measurable yet. hypothesis It should start to matter at long contexts.

Is it right?

Fast and wrong is worthless, so correctness gates everything. On the CPU (through the HIP-CPU runtime, so it also runs in free CI), every kernel is checked against a reference on awkward shapes, the tokenizer against OpenAI's, and the whole engine against a float64 NumPy implementation of a tiny random GPT-2. On the GPU, the test sweep adds shapes up to 2049 × 1023 × 515.

Against PyTorch on the real GPT-2 weights, the largest logit difference is (tolerance 1e-2), and the greedy tokens are identical for steps. Getting there found one real bug, and it wasn't in the C++. The script that exports the weights skipped any tensor whose name ends in attn.bias, meaning to drop an internal mask buffer. That also matched attn.c_attn.bias, the real attention bias in every layer, which silently disappeared. Matching on .attn.bias with the leading dot fixed it.

Keeping it honest: performance CI

A benchmark nobody re-runs goes stale. On every push, GitHub Actions builds and tests on the CPU backend and compile-checks the ROCm build. A self-hosted GPU job reruns the benchmarks and fails the build if any kernel gets more than 7% slower than the committed baseline. On the 4060, the spread between back-to-back runs of v4 at 4096 was about %, so 7% leaves room for noise. Each run's results go to a history chart.

What's next

  • AMD Instinct MI300X. Run the same code on gfx942, where v5 uses real MFMA instructions, with profiles from rocprof-compute. That's part 2.
  • Profile every stage and replace each hypothesis above with what the counters say.
  • Faster decode: split-K matrix-vector kernels for more parallelism, and FP16 or INT8 weights, which directly shrink the ~500 MB read per token.
  • A better v5: transposed B in LDS, larger tiles and deeper pipelining.

How this was built

I built this project with AI coding agents (Claude Code) writing much of the code under my direction. Every number on this page comes from a JSON file in the repo, produced by running the code on my own RTX 4060. Reproduce them with:

cmake -S . -B build -DCMAKE_HIP_PLATFORM=nvidia -DCMAKE_HIP_ARCHITECTURES=89
cmake --build build -j && ctest --test-dir build
./build/gemm_bench --kernel all --out results
./build/gpt2 --model models/gpt2 --prompt "Once upon a time" --max-new-tokens 64

Windows users can run the whole thing in Docker with GPU passthrough. docs/SETUP.md has the commands.
